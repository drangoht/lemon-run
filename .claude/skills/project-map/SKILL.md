# Project map -- Lemon Run

This map says **where** each thing is. For the rest: `docs/GDD.md` (**why** the game is tuned this
way) - `docs/PITFALLS_UNITY.md` (index of the **pitfalls**, open the domain) - `CLAUDE.md` (current
phase and conventions).

> **Keep this map up to date**: as soon as you add, remove or rename a system, a screen, a piece of
> data or a tool, update the relevant section **in the same commit**. A stale map is worse than no
> map -- it gives a wrong answer with authority. When in doubt, check the file before asserting it;
> do not copy blindly.

> WARNING: **ceiling: ~150 lines.** This map is loaded in full at every invocation, and it grows
> with the project -- measured at 12 KB on a small game, that is 3,000 tokens reloaded every time
> someone looks for a file. It says **where**, in one line per entry. The *how* belongs to the code,
> the *why* to the GDD. Beyond the ceiling, move the checklists out to a neighbouring file rather
> than making this one longer.

## sec. Rules -- `Assets/Scripts/Rules/`

Pure logic, no engine dependency, **tested**. This is where every numeric rule of the game lives.

- `Lanes` -- lane numbering and lateral position; a step into the edge is refused, never wrapped.
- `LaneTravel` -- progress of a lane change and its easing.
- `JumpArc` -- height during a jump; fixed duration, not a physics simulation.
- `RunPace` -- speed as a function of distance run: a ramp, then flat.
- `ObstacleRules` -- what a row allows, whether a hit lands, and the CROSSING of a row.
- `RowDraw` -- draws rows around a guaranteed, reachable opening. Deterministic: same seed,
  same road.
- `RowSpacing` -- gap between rows expressed as a reaction window in seconds, not in units.
- `Lead` -- the lead in SECONDS: what a hit costs, what fruit buys back, the gauge fraction,
  and the gap at which the pursuer is DRAWN (not the real one -- see gdd/pursuer.md).
- `FruitPlacement` -- which lane may carry a fruit (NEVER the free one, GDD section 5) and the
  reach at which it is swallowed.
- `Score` -- distance run plus fruit swallowed.
- `RunnerTuning` -- every tunable value of the running, obstacle, pursuer and fruit systems.

## sec. Gameplay -- `Assets/Scripts/Gameplay/`

- `Runner` -- reads the keys, holds the lane and jump state, moves the runner. Delegates every
  number to `Rules/`.
- `CameraRig` -- keeps the camera behind and above, following a lane change only halfway.
- `GroundTreadmill` -- recycles the road tiles in front of the runner; the tiles are its children,
  placed by `SceneBuilder`.
- `ObstacleField` -- lays the rows ahead (obstacles AND their fruit: the fruit is tied to a
  blocked lane, so it cannot be placed without the row), takes them back behind, and decides what
  the runner ran into or swallowed. Pools its pieces.
- `Pursuer` -- holds the lead, drains it on each hit, and places itself in a band that keeps it
  framed. WARNING: its on-screen distance is NOT the lead.
- `RunSession` -- watches for the catch, freezes the runner, shows the panel, restarts by
  reloading the scene.

## sec. UI -- `Assets/Scripts/UI/`

- `BuildStampLabel` -- the version stamp, bottom LEFT (bottom right belongs to Unity's watermark).
- `RunDebugLabel` -- TEMPORARY debug readout (lane, speed, distance, hits, lead).
- `LeadGauge` -- the lead bar. The ONLY honest reading of how close the pursuer is.
- `RunOverLabel` -- the end-of-run panel: distance run, and the key to go again.

## sec. Data

- `Build/Windows/tuning.json` -- written by the game on its first run from `RunnerTuning` defaults,
  re-read at every launch. Changing a value costs a relaunch, not a rebuild.
  WARNING: it sits beside the binary, which the build overwrites -- a scratch pad for a session,
  not a place to keep a setting. What is worth keeping goes back into `RunnerTuning`.
  WARNING: `LaneWidth` is the exception -- the road geometry bakes it at build time, so changing it
  there slides the runner off the painted lanes. That one needs a rebuild.

## sec. Tools -- `tools/`

| Tool | What it does |
|---|---|
| `build.ps1` | **Builds** (Windows/web), and `-Run` chains on to the capture. The only caller of Unity |
| `configure.ps1` | Says where Unity, Python, dotnet and butler are -- and what is missing |
| `environment.ps1` | Resolves and remembers those paths (`local.settings.json`, out of git). Dot-source it |
| `release_itch.ps1` | Publishes a version (build -> butler push -> commit). `/publish-itch` skill |
| `serve_web.py` | Serves `Build/Web` **without browser cache** -- indispensable after a rebuild |
| `drive_game.py` | Launches the Windows build, injects keys, captures the window |

WARNING: **no external tool path hard-coded anywhere**: `Unity.exe` is not in the same place from
one machine to the next. Everything goes through `environment.ps1`.

## Wiring checklists

Content added "halfway" raises no error: it is simply inert. Keep here the list of points to touch
for each type of addition.

**Adding a piece of content** (example to adapt):
1. The data (JSON / ScriptableObject).
2. The matching rule in `Rules/` **and its test**.
3. The engine wiring (`Gameplay/`).
4. The **sound** -- WARNING: an entry missing from the audio table is silent, with no error.
5. The **sprite** -- WARNING: check `Resources/` vs `Art/`, getting it wrong shows nothing abnormal.
6. The **text** (name, description) and its localisation key.
7. Updating this map, in the same commit.
